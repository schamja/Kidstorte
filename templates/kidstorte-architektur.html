Architektur · LangGraph-Pattern

Nodes · Edges · Shared State

Jede Kundeninteraktion durchläuft einen kontrollierten Graph spezialisierter Verarbeitungsschritte. Keine Black-Box — jede Entscheidung ist nachvollziehbar.

Analogie: Stell dir eine Bäckerei vor. Der Graph ist der Chef-Konditor — er entscheidet, wer als Nächstes dran ist. Die Nodes sind die Mitarbeiter — jeder hat eine spezielle Aufgabe. Die Services sind die Werkzeuge (Ofen, Kühlschrank, Telefon). Der State ist das Bestellformular, das von Hand zu Hand weitergereicht wird.

15 spezialisierte Verarbeitungsschritte

Jeder Schritt hat einen klaren Job.

Statt einer einzigen "do-everything"-Prompt-Logik wird jede Verantwortung in eine eigene, isoliert testbare Node ausgelagert.

NODE 0 · GUARDRAIL
guardrail
Filtert jede Eingabe — blockiert Beleidigungen, Jailbreaks, Spam. Erlaubt Deko-Wünsche.
NODE 1 · CLASSIFY
classify_and_extract
Erkennt Intent & extrahiert Bestellinfos in einem einzigen LLM-Call. ~50% Kostenersparnis.
NODE 2 · GREET
greet
Begrüßt den Kunden, startet eine neue Session, setzt question_todo zurück.
NODE 3 · ORDER
extract_info
Extrahiert Anlass, Gäste, Geschmack, Form per LLM aus der Nachricht.
NODE 4 · GATE
check_complete
Prüft welche der 10 Pflichtfelder fehlen — gating für Bestell-Abschluss.
NODE 5 · LOOP
ask_next
Fragt nach der nächsten fehlenden Info — bestätigt zuerst, was der Kunde gesagt hat.
NODE 6 · SUMMARY
summarize_order
Fasst die komplette Bestellung zusammen, sobald alle Infos vorhanden sind.
NODE 7 · RAG
retrieve_docs
Sucht relevante Dokumente in ChromaDB per Embedding-Similarity (Top-5).
NODE 8 · PRICE
calculate_price
Berechnet den Gesamtpreis aus Bestellinfos + RAG-Kontext. Temperature 0.
NODE 9 · INFO
answer_question
Beantwortet allgemeine Fragen (Allergene, Öffnungszeiten, Lieferung) per RAG.
NODE 10 · IMAGE
generate_image
Generiert Vorschau-Bild mit gpt-image-1, Fallback HuggingFace FLUX.
NODE 11 · CHANGE
update_order
Verarbeitet Änderungswünsche — Farbe, Form, Größe — vergleicht vorher/nachher.
NODE 12 · CALENDAR
check_calendar
Prüft Liefertermin-Verfügbarkeit via SQLite-Kapazität oder cal.com API.
NODE 13 · FINALIZE
finalize_order
Adressformular, Speicherung in SQLite, automatische E-Mail mit PDF-Anhang.
NODE 14 · OFFTOPIC
redirect
Lenkt höflich zurück zum Thema. Feste Antwort aus Config — spart LLM-Kosten.

class OrderInfo(BaseModel):
    anlass:       str | None = None
    gaeste:       int | None = None
    geschmack:    str | None = None
    form:         str | None = None
    schichten:    int | None = None
    fuellung:     str | None = None
    dekoration:   str | None = None
    allergien:    list[str] = []
    abholung:     str | None = None

class AgentState(BaseModel):
    user_input:    str
    messages:      list[Message] = []
    intent:        Intent | None = None
    order_info:    OrderInfo = OrderInfo()
    context:       str | None = None
    price:         Decimal | None = None
    image_url:     str | None = None
    order_complete: bool = False

# Routing — welcher Node kommt als nächstes?

def route_after_classify(state: AgentState) -> str:
    match state.intent:
        case Intent.GREETING:  return "greet"
        case Intent.ORDER:     return "extract_info"
        case Intent.PRICE:     return "retrieve_docs"
        case Intent.IMAGE:     return "generate_image"
        case Intent.INFO:      return "retrieve_docs"
        case Intent.FINALIZE:  return "check_calendar"
        case Intent.OFFTOPIC:  return "redirect"
        case _:                   return "redirect"

def route_after_check_complete(state) -> str:
    if state.order_info.is_complete():
        return "summarize_order"
    return "ask_next"      # Schleife
app/nodes.py · classify_and_extract 
# Eine typische Node — erkennt Intent & extrahiert Daten in einem einzigen LLM-Call.
# Hot-reloadbarer Prompt aus YAML, strikt typisierte Antwort, kein freier Text.

async def classify_and_extract(state: AgentState) -> AgentState:
    prompt = prompts.render("classify_and_extract", user_input=state.user_input)

    response = await openai.chat.completions.create(
        model="gpt-4o-mini",
        response_format={"type": "json_object"},
        temperature=0,
        messages=[
            {"role": "system", "content": prompt.system},
            {"role": "user",   "content": state.user_input},
        ],
    )

    parsed = ClassifyResponse.model_validate_json(response.choices[0].message.content)

    state.intent = parsed.intent
    state.order_info = state.order_info.merge(parsed.extracted)

    track_metrics(node="classify_and_extract", tokens=response.usage.total_tokens)
    return state
Debugging in der Praxis · Real-World Beispiel

Ein State-Bug — und warum ich ihn in drei Schichten fixe.

Bei einem System mit 14 Nodes und einem geteilten State entstehen Bugs nicht im LLM, sondern in den Übergängen zwischen Nodes. Hier ein konkretes Beispiel — wie ich es diagnostiziert und behoben habe.

01 · Symptom
Quick-Option-Buttons erschienen nach der Bestellung
Die Karte "Abholung oder Lieferung" tauchte wieder auf, obwohl die Bestellung bereits komplett zusammengefasst war — auch bei späteren Folge-Fragen zum Preis oder Liefertermin.
"Es taucht wieder dieser Button mit Abholung und Lieferung auf, ich dachte, du hast den Bug entfernt."
02 · Diagnose
State wird gesetzt, aber nicht geleert
state["current_field"] wurde nur in ask_next gesetzt — beim Abbiegen zu summarize_order blieb der alte Wert in ChromaDB-Session erhalten. Frontend bekam in jedem Folgeturn dasselbe Feld. 
# Buggy Flow:
ask_next     → state["current_field"]="abholung"
summarize    → # vergisst zu leeren ✗
calc_price   → state["current_field"] # noch da
finalize     → state["current_field"] # noch da
                → Buttons rendern erneut ✗
03 · Fix · 3 Schichten
Wurzel beheben + zweimal abdichten
  1. Quelle · nodes.py summarize_order setzt current_field = ""
  2. Filter · main.py Helper _safe_current_field() sendet stale Felder gar nicht erst an das Frontend
  3. Defense · script.js UI prüft selbst: order_info[field] oder order_complete → keine Buttons
★
Lehre: Bei verteilten States (LangGraph, Redux, Session-Storage) ist es nicht die Frage ob ein Feld stale wird, sondern wann. Robust ist nicht „eine perfekte Stelle finden", sondern an Quelle, Schnittstelle und UI alle drei abdichten — so bleibt das System auch beim nächsten Refactor verlässlich.
