1RAG im Projekt
FWas ist RAG und warum nutzen Sie es?▾

RAG heisst Retrieval Augmented Generation. Die Idee ist einfach: Statt dem KI-Modell alle Infos beizubringen, holen wir die passenden Infos aus einer Datenbank und geben sie dem Modell als "Spickzettel" mit.

Beispiel aus Kidstorte: Wenn ein Kunde fragt "Was kostet eine Schokoladentorte?" — dann sucht das System in unserer Wissensdatenbank nach Preisen, findet "Schokoladentorte M: 45€, L: 55€" und gibt das dem LLM. So bekommt der Kunde den echten Preis statt einer ausgedachten Zahl.

Einfach merken: RAG = "Nachschlagen statt Raten"
FWie funktioniert der RAG-Ablauf technisch?▾

Drei Schritte:

  1. Vorbereitung (einmalig): Unsere Produktdokumente (Preise, Allergien, Infos) werden in kleine Stücke ("Chunks") zerlegt. Jeder Chunk wird in einen Zahlenvektor umgewandelt (Embedding) und in ChromaDB gespeichert.
  2. Suche (bei jeder Frage): Die Kundenfrage wird auch in einen Vektor umgewandelt. Dann suchen wir die 5 ähnlichsten Chunks per Cosine Similarity.
  3. Antwort: Die gefundenen Chunks werden dem LLM als Kontext mitgegeben. Das LLM antwortet basierend auf diesen echten Daten.
Kundenfrage → Embedding → Vektorsuche in ChromaDB → Top-5 Chunks → LLM + Kontext → Antwort
FWelches Embedding-Modell und warum?▾

text-embedding-3-small von OpenAI. Es wandelt Text in einen Vektor mit 1536 Dimensionen um.

Warum dieses? Es kostet nur $0.02 pro 1 Million Tokens — also fast nichts. Für unsere ~100 Produktdokumente ist es mehr als ausreichend. Größere Modelle wie text-embedding-3-large wären unnötiger Overhead.

FWann wird RAG ausgelöst und wann nicht?▾

RAG wird NUR bei zwei Intents aktiviert:

  • price — "Was kostet meine Torte?"
  • info — "Habt ihr glutenfreie Optionen?"

Bei order, change, greeting wird kein RAG gemacht. Warum? Weil wir dort kein Produktwissen brauchen — nur die Bestellinfos des Kunden. Das spart Embedding-Kosten bei jeder Nachricht.

Bonus: Wir nutzen ChromaDB für zwei Zwecke: Produktwissen (Collection cake_chunks) UND Session-Speicherung (Collection sessions). Eine Technologie, zwei Aufgaben.

2LangGraph / State Machine
FNutzen Sie LangGraph als Library?▾

Nein. Wir haben einen eigenen Graphen gebaut, der nach dem gleichen Prinzip funktioniert. In graph.py (~300 Zeilen) steuern wir den kompletten Ablauf.

Warum selbst gebaut?

  • Volle Kontrolle — wir verstehen jede Zeile
  • Keine Library-Abhängigkeit — kein Risiko durch Breaking Changes
  • Einfacher zu debuggen

Das Prinzip ist aber identisch: Stateless Nodes, die einen State-Dict empfangen, verarbeiten und zurückgeben.

FWie sieht der Bestellablauf aus?▾
Kunde schreibt etwas → Guardrail (Sicherheitscheck) → classify_and_extract (Was will der Kunde? + Daten extrahieren) → ROUTING je nach Intent: greeting → Begrüßung order → Felder prüfen → nächste Frage stellen ODER Zusammenfassung price → Wissensdatenbank durchsuchen → Preis berechnen image → Tortenbild generieren info → Wissensdatenbank → Frage beantworten change → Bestellung ändern finalize → Adressformular zeigen offtopic → Höflich zurücklenken

Das Besondere: Bei order gibt es eine Schleife — der Bot fragt so lange nach fehlenden Infos, bis alle 10 Pflichtfelder ausgefüllt sind.

FWas ist der AgentState?▾

Ein Python-Dictionary, das alle Informationen enthält, die durch den Graphen fließen. Wie ein "Klemmbrett", das jeder Node lesen und beschreiben kann:

  • user_input: Was der Kunde geschrieben hat
  • messages: Der gesamte Chatverlauf
  • intent: Was der Kunde will (order, price, info...)
  • order_info: Die Bestelldetails (Geschmack, Form, Schichten...)
  • question_todo: Welche Felder schon gefragt/beantwortet sind
  • missing_fields: Was noch fehlt
  • order_complete: Sind alle Felder voll?
  • context: RAG-Ergebnisse (Produktinfos)
  • image_url: Generiertes Tortenbild
FErklären Sie das question_todo-System.▾

Das ist unser Fortschrittstracker. Jedes Pflichtfeld hat einen Status:

pending → Bot hat noch nicht danach gefragt asked → Bot hat gefragt, Kunde hat noch nicht geantwortet answered → Kunde hat geantwortet, Feld ist gefüllt

Warum? Damit der Bot nie zweimal die gleiche Frage stellt. Wenn geschmack: "answered" ist, fragt er nicht nochmal "Welchen Geschmack möchten Sie?"

Die 10 Pflichtfelder: Anlass, Gäste, Geschmack, Form, Schichten, Füllung, Dekoration, Allergien, Beschriftung, Abholung

FWarum sind die Nodes "stateless"?▾

Stateless heisst: Jeder Node speichert nichts intern. Er bekommt den kompletten State als Input, macht seine Arbeit, und gibt den geänderten State zurück.

Vorteile:

  • Testbar: Man kann einen Node isoliert testen mit einem künstlichen State
  • Debuggbar: Wenn etwas schiefgeht, kann man den State kopieren und den Fehler nachstellen
  • Skalierbar: Theoretisch könnte man mehrere Server betreiben, weil der State nicht im Speicher hängt

3LLM-Strategie
FWelches Modell nutzen Sie und warum genau das?▾

gpt-4o-mini für alle Aufgaben.

Warum? Es ist 33x günstiger als GPT-4o ($0.15 vs $5.00 pro 1M Input-Tokens). Für unsere Aufgaben — Intent erkennen, Felder extrahieren, Fragen generieren — brauchen wir kein teures Top-Modell. gpt-4o-mini ist schlau genug.

Kosten pro Nachricht: ca. $0.0003 (weniger als ein Hundertstel Cent)

FWie viele LLM-Calls gibt es pro Nachricht?▾

Typisch nur 2 Calls:

  1. classify_and_extract — erkennt Intent UND extrahiert Daten in einem Call
  2. ask_next — generiert die nächste Frage

Das war eine wichtige Optimierung: Früher waren das 2 getrennte Calls (Intent + Extraktion). Durch die Kombination sparen wir 50% LLM-Kosten pro Nachricht.

Merken: "Wir haben Intent-Klassifikation und Feld-Extraktion in einem einzigen LLM-Call kombiniert, um Kosten zu halbieren."
FWie steuern Sie die Temperature?▾

Temperature bestimmt, wie "kreativ" das LLM antwortet:

TemperatureWo eingesetztWarum
0Intent-Erkennung, JSON-Extraktion, PreisImmer gleiche, zuverlässige Antwort — kein Raten
0.3Info-AntwortenLeichte Variation, aber noch faktisch
0.6Fragen an den KundenNatürlich, freundlich, nicht roboterhaft
Faustregel: Je wichtiger Genauigkeit, desto niedriger die Temperature.
4Prompt Engineering
FWo werden die Prompts verwaltet?▾

In prompts_config.yaml — einer YAML-Datei. Der Clou: Sie ist hot-reloadable. Das heisst, der Admin kann Prompts live bearbeiten, ohne den Server neu zu starten. Bei jedem Zugriff prüft der Code: "Hat sich die Datei geändert? Wenn ja, neu laden."

FWie verhindern Sie, dass das LLM Sachen erfindet?▾

Vier Schutzmaßnahmen gegen Halluzinationen:

  1. Klare Verbote im Prompt: "ERFINDE NIEMALS Werte die der Kunde nicht gesagt hat"
  2. RAG für Fakten: Preise kommen aus der Datenbank, nicht aus dem Modell
  3. JSON-Format erzwingen: Das LLM gibt nur vorgegebene Felder zurück, keinen Freitext
  4. JSON-Repair: Wenn das JSON kaputt ist, schicken wir es nochmal ans LLM: "Bitte korrigiere dieses JSON"
FWie gehen Sie mit mehrdeutigen Eingaben um?▾

Der Prompt hat klare Regeln für Sonderfälle:

  • "ja" → Schaut auf die letzte Bot-Frage. Wenn Bot nach Beschriftung fragte → Intent = order
  • "3" → Wenn Bot nach Schichten fragte → {schichten: "3"}
  • "Ronaldo" → Kein Off-topic! Das ist eine Dekoration für die Torte → Intent = order
  • Tippfehler → "Schokolde" wird zu "Schokolade" korrigiert. Aber Namen wie "Aron" bleiben wie sie sind
5Session Management
FWie behalten Sie den Bestellstand zwischen Nachrichten?▾

Nach jeder Nachricht wird der komplette State als JSON in ChromaDB gespeichert. Bei der nächsten Nachricht wird er wieder geladen.

Der Ablauf:

  1. Kunde schickt Nachricht
  2. Server holt Session-ID aus dem Cookie
  3. Laden: session_mgr.load_session(session_id) → State aus ChromaDB
  4. Graph durchlaufen
  5. Speichern: session_mgr.save_session(session_id, state) → State in ChromaDB

Cookie: cake_session_id, HTTPOnly (nicht per JavaScript lesbar), 24 Stunden gültig.

FWas passiert mit alten Sessions?▾

cleanup_old_sessions() löscht automatisch Sessions, die älter als 24 Stunden sind. Außerdem beschränken wir den Chatverlauf auf max 20 Nachrichten — ältere werden gelöscht, um Kosten zu sparen (weniger Tokens an das LLM schicken).

6Bildgenerierung
FWie erstellen Sie die Tortenvorschau-Bilder?▾

Eine Provider-Chain mit Fallback:

1. OpenAI gpt-image-1 (beste Qualität) ├─ Erfolg → Bild speichern, fertig ├─ Moderation-Block → Prompt bereinigen, Fallback └─ Rate-Limit → 15s warten, retry 2. HuggingFace FLUX.1-schnell (Fallback) └─ HuggingFace SDXL (zweiter Fallback)

Der Bild-Prompt wird vom LLM generiert: Es bekommt die Bestelldetails (Form, Farbe, Geschmack, Dekoration) und baut daraus eine detaillierte Bildbeschreibung.

FWie lösen Sie das Problem mit Personennamen?▾

OpenAI blockiert Bilder von echten Personen. Unsere Lösung: Namen in Figur-Beschreibungen umwandeln:

  • "Ronaldo" → "famous soccer player figurine made of fondant"
  • "Elsa" → "ice queen princess figurine"

Das Wort "figurine" ist der Schlüssel — es signalisiert dem Modell: Das ist eine Tortenfigur, keine echte Person.

FGibt es ein Referenzbild-System?▾

Ja! Wir haben einen Bilder/-Ordner mit früheren Torten. Die Funktion _find_best_reference() sucht automatisch ein passendes Referenzbild per Dateinamen-Matching:

  • +2 Punkte für passende Figur (z.B. "elsa" im Dateinamen)
  • +1 für passende Etagenzahl (z.B. "3_etagen")
  • +1 für passende Farbe

Ab Score ≥2 wird das Referenzbild dem Kunden gezeigt. Kein LLM nötig — rein regelbasiert und kostenlos.

7Kostenoptimierung
FWelche 5 Strategien nutzen Sie zur Kostenoptimierung?▾
  1. Günstiges Modell: gpt-4o-mini statt GPT-4o → 33x billiger
  2. Combined Call: Intent + Extraktion in einem LLM-Call statt zwei → 50% weniger Calls
  3. Response Cache: Gleiche Fragen werden nicht doppelt berechnet (SHA256-Hash als Schlüssel, 200 Einträge, 1h gültig)
  4. Selektives RAG: Wissensdatenbank nur bei Preis- und Info-Fragen durchsuchen
  5. Message Truncation: Nur die letzten 20 Nachrichten mitschicken, max 3000 Tokens
Ergebnis: Eine komplette Bestellung (8-12 Nachrichten) kostet unter $0.004 — weniger als ein halber Cent.
8LangSmith & Monitoring
FWas tracen Sie mit LangSmith?▾

Drei Ebenen:

  1. Node-Level: Jeder Node wird getrackt — was rein geht, was raus kommt, wie lange es dauert
  2. LLM-Level: Jeder LLM-Call wird aufgezeichnet — welcher Prompt, welche Antwort, welches Modell
  3. Graph-Level: Der gesamte Ablauf von Kundenfrage bis Bot-Antwort

Sichtbar unter smith.langchain.com im Projekt "Kidstorte".

FWas passiert wenn LangSmith ausfällt?▾

Nichts Schlimmes! Graceful Degradation — wenn LangSmith nicht erreichbar ist, läuft der Bot ganz normal weiter, nur ohne Tracing. Das ist bewusst so implementiert: LangSmith ist ein "Nice-to-have", kein Single Point of Failure.

9Sicherheit & Fehlerbehandlung
FWie schützen Sie vor Prompt Injection?▾

Der guardrail()-Node ist der allererste Schritt im Graphen. Bevor irgendetwas passiert, prüft er:

  • Ist die Nachricht länger als 800 Zeichen? → Spam blockieren
  • Versucht jemand das System zu manipulieren? ("Ignoriere alle Anweisungen") → Blockieren
  • Enthält die Nachricht missbräuchliche Inhalte? → Blockieren

Wenn blockiert: guardrail_blocked = True, der Rest des Graphen wird nicht durchlaufen.

FWas passiert bei API-Fehlern?▾

Drei Schutzschichten:

  1. Retry: Bei Rate-Limits oder Timeouts: 3 Versuche mit steigender Wartezeit (5s, 10s, 20s)
  2. @safe_node: Jeder Node ist mit einem Decorator abgesichert. Bei jedem unerwarteten Fehler gibt er eine freundliche Meldung zurück statt abzustürzen
  3. Fallback: Bei Bildgenerierung: OpenAI fällt aus? → HuggingFace übernimmt

FWarum FastAPI statt Flask?▾

  • Streaming: Wort-für-Wort-Antworten (SSE) sind einfach umzusetzen

Theoretische Fragen: LLM, Transformer, RAG, LangChain, LangGraph, LangSmith, Agenten

1LLM — Grundlagen
FWas ist ein LLM? Erklären Sie es einfach.▾

Ein Large Language Model ist ein riesiges KI-Programm, das gelernt hat, wie Sprache funktioniert. Es wurde mit Milliarden von Texten aus dem Internet trainiert — Bücher, Webseiten, Wikipedia.

Wie funktioniert es? Es sagt das nächste Wort voraus. Wenn es "Der Himmel ist" liest, sagt es "blau" voraus. Das klingt einfach, aber bei Milliarden Parametern kann es erstaunlich kluge Texte generieren.

Einfach: "Ein LLM ist wie ein sehr belesener Assistent, der basierend auf dem Gelesenen Texte weiterschreiben kann."
FWas ist ein Token?▾

Ein Token ist ein Textstück, das das LLM als eine Einheit verarbeitet. Nicht immer ein ganzes Wort:

  • "Hallo" = 1 Token
  • "Schokoladentorte" = 3-4 Tokens (wird aufgeteilt)
  • "Hello world" = 2 Tokens

Faustregel Deutsch: 1 Token ≈ 3 Zeichen
Faustregel Englisch: 1 Token ≈ 4 Zeichen

Warum wichtig? Tokens bestimmen den Preis (man zahlt pro Token) und das Limit (wie viel Text das LLM auf einmal verarbeiten kann).

FWas ist Tokenization? Wie werden Tokens erstellt?▾

Tokenization ist der Prozess, Text in Tokens zu zerlegen. Die gängigste Methode ist BPE (Byte Pair Encoding):

  1. Start: Jeder Buchstabe ist ein Token ("H", "a", "l", "l", "o")
  2. Die häufigsten Buchstabenpaare werden zusammengefasst: "l"+"l" → "ll"
  3. Das wird wiederholt, bis man ein Vokabular mit ~50.000-100.000 Tokens hat

Ergebnis: Häufige Wörter wie "the" sind ein Token. Seltene Wörter werden in Teile zerlegt.

Andere Methoden: WordPiece (BERT nutzt das), SentencePiece (funktioniert ohne Leerzeichen, gut für Japanisch/Chinesisch)

FWas ist das Context Window?▾

Das Context Window ist wie das "Kurzzeitgedächtnis" des LLMs — wie viele Tokens es gleichzeitig "sehen" kann.

ModellContext WindowUngefähr in Text
GPT-3.516K Tokens~12.000 Wörter / ~25 Seiten
GPT-4o-mini128K Tokens~96.000 Wörter / ~200 Seiten
GPT-4.11M Tokens~750.000 Wörter / ~1500 Seiten

Wichtig: Input + Output zählen zusammen! Wenn das Fenster voll ist, "vergisst" das Modell ältere Inhalte.

FWas ist Temperature?▾

Temperature steuert die "Kreativität". Stellen Sie sich eine Würfel vor:

  • Temperature 0: Der Würfel fällt immer auf die gleiche Seite. Deterministisch. Perfekt für Fakten.
  • Temperature 0.7: Der Würfel ist leicht unfair, bevorzugt gute Antworten, aber erlaubt Variation.
  • Temperature 1.5: Der Würfel ist wild. Kreative, aber manchmal unsinnige Antworten.
"Für JSON und Klassifikation nehme ich Temperature 0. Für natürliche Chatantworten 0.6."
FWas sind Top-p und Top-k?▾

Neben Temperature gibt es zwei weitere Regler für die Textgenerierung:

Top-k: Das Modell wählt nur aus den k wahrscheinlichsten nächsten Tokens. Top-k=50 heisst: Nur die besten 50 Optionen. Die restlichen werden ignoriert.

Top-p (Nucleus Sampling): Das Modell wählt aus den wahrscheinlichsten Tokens, bis ihre kumulative Wahrscheinlichkeit p erreicht. Top-p=0.9 heisst: Nimm die Top-Tokens deren Wahrscheinlichkeiten zusammen 90% ergeben.

In der Praxis: Temperature + Top-p reichen. Top-k wird selten manuell gesetzt.
FWas sind Halluzinationen?▾

Das LLM erfindet Fakten, die nicht stimmen — aber klingt dabei total überzeugend. Beispiel: "Der Eiffelturm ist 412 Meter hoch" (richtig: 330m).

Warum passiert das? Das LLM sagt das wahrscheinlichste nächste Wort voraus. Es "weiß" nicht, was wahr ist — es weiß nur, was "plausibel klingt".

5 Gegenmaßnahmen:

  1. RAG — Echte Fakten aus einer Datenbank liefern
  2. Temperature 0 — Weniger "Kreativität" = weniger Erfindungen
  3. Explizite Prompts — "Sage nur etwas, wenn du eine Quelle hast"
  4. Strukturierte Outputs — JSON erzwingen statt Freitext
  5. Grounding — Quellen zitieren lassen

FFine-Tuning vs. Prompting — Unterschied?▾

Prompting (was wir nutzen): Man gibt dem Modell Anweisungen im Text. "Du bist ein Tortenberater, antworte auf Deutsch." Kein Training nötig, sofort änderbar, günstig.

Fine-Tuning: Man trainiert das Modell auf eigenen Daten weiter. Braucht 100-1000+ Beispiele, dauert Stunden, ist teuer.

"Für 95% aller Anwendungen reicht Prompting. Fine-Tuning nur wenn man eine sehr spezifische Sprache oder ein besonderes Format braucht."
FWas ist RLHF?▾

Reinforcement Learning from Human Feedback — so wird ein LLM "höflich" und "hilfreich" gemacht.

3 Schritte:

  1. Pre-Training: Modell lernt Sprache aus dem Internet (unsupervised)
  2. Supervised Fine-Tuning: Menschen schreiben gute Beispiel-Antworten, Modell lernt davon
  3. RLHF: Menschen bewerten Antwort-Paare ("A ist besser als B"). Ein Reward-Modell lernt diese Präferenzen. Das LLM wird optimiert, damit es Antworten gibt, die Menschen gut finden.

Ergebnis: Das Modell ist nicht nur schlau, sondern auch hilfreich, ehrlich und ungefährlich.

FSystem-Prompt, User-Prompt, Assistant — was ist was?▾

Jeder LLM-Aufruf besteht aus einer Liste von Nachrichten:

[ {"role": "system", "content": "Du bist ein Tortenberater..."}, {"role": "user", "content": "Ich will eine Schokotorte"}, {"role": "assistant", "content": "Gerne! Welche Größe?"}, {"role": "user", "content": "Für 10 Personen"} ]
  • system: Die "geheimen Anweisungen" — definiert Rolle und Regeln
  • user: Was der Kunde schreibt
  • assistant: Vorherige Bot-Antworten (für Kontext)
2Transformer-Architektur
FWas ist ein Transformer?▾

Der Transformer ist die Architektur hinter allen modernen LLMs (GPT, Claude, Llama, Gemini). Er wurde 2017 von Google im Paper "Attention Is All You Need" vorgestellt.

Kernidee: Statt Text Wort für Wort zu verarbeiten (wie frühere Modelle), kann der Transformer alle Wörter gleichzeitig betrachten und deren Beziehungen zueinander lernen.

"Der Transformer kann bei jedem Wort auf alle anderen Wörter im Text schauen — das nennt man Self-Attention."
FWas ist Self-Attention? Einfach erklärt.▾

Stellen Sie sich vor, Sie lesen den Satz: "Die Torte ist für meinen Sohn, er wird 5."

Self-Attention bedeutet: Das Modell lernt, dass "er" sich auf "meinen Sohn" bezieht. Jedes Wort "schaut" auf alle anderen Wörter und gewichtet: "Wie wichtig ist das andere Wort für mein Verständnis?"

Technisch (vereinfacht):

  1. Jedes Wort wird in 3 Vektoren umgewandelt: Query (was suche ich?), Key (was biete ich?), Value (welchen Inhalt habe ich?)
  2. Für jedes Wortpaar: Query × Key = Attention Score (wie relevant?)
  3. Die Scores werden normalisiert (Softmax) und mit den Values gewichtet
FWas ist Multi-Head Attention?▾

Statt nur eine Attention zu berechnen, berechnet der Transformer mehrere parallel (z.B. 12 oder 96 "Heads").

Warum? Jeder Head kann einen anderen Aspekt der Sprache lernen:

  • Head 1: lernt grammatische Beziehungen (Subjekt ↔ Verb)
  • Head 2: lernt Pronomen-Referenzen ("er" → "Sohn")
  • Head 3: lernt Nähe-Beziehungen (benachbarte Wörter)

Am Ende werden alle Heads zusammengesetzt → reicheres Verständnis.

FWas ist Positional Encoding?▾

Das Problem: Der Transformer verarbeitet alle Wörter gleichzeitig, aber Reihenfolge ist wichtig ("Hund beisst Mann" ≠ "Mann beisst Hund").

Lösung: Positional Encoding — zu jedem Wort-Vektor wird ein "Positions-Signal" addiert, das dem Modell sagt: "Dieses Wort steht an Position 1, dieses an Position 2, ..."

GPT nutzt gelernte Positional Embeddings — das Modell lernt selbst, welche Positionspatterns wichtig sind.

FWas ist der KV-Cache?▾

Bei der Textgenerierung erzeugt das LLM Token für Token. Ohne Optimierung müsste es bei jedem neuen Token die Attention für alle vorherigen Tokens neu berechnen.

KV-Cache: Die Key- und Value-Vektoren der vorherigen Tokens werden gespeichert. Bei jedem neuen Token muss nur die Attention für das neue Token berechnet werden.

Ergebnis: Viel schnellere Generierung, aber braucht GPU-Speicher.

3RAG — Theorie
FErklären Sie RAG Schritt für Schritt.▾

RAG = Retrieval Augmented Generation

Stellen Sie sich eine Prüfung vor: Statt alles auswendig zu wissen (reines LLM), darf man ein Buch mitbringen (RAG). Man schaut die Antwort nach und formuliert sie dann in eigenen Worten.

1. INDEXING (einmalig): Dokumente → Chunks → Embedding-Modell → Vektoren → Datenbank 2. RETRIEVAL (bei jeder Frage): Kundenfrage → Embedding → Vektorsuche → Top-5 passende Chunks 3. GENERATION: Prompt = "Beantworte basierend auf diesem Kontext: [Chunks]" → LLM generiert Antwort
FWas ist ein Embedding genau?▾

Ein Embedding ist eine Liste von Zahlen (z.B. 1536 Zahlen), die die Bedeutung eines Textes darstellt.

Das Geniale: Ähnliche Texte haben ähnliche Zahlenlisten:

  • "Schokoladentorte" und "Chocolate Cake" → Vektoren zeigen in fast die gleiche Richtung
  • "Schokoladentorte" und "Autoversicherung" → Vektoren zeigen in völlig verschiedene Richtungen

Das ermöglicht semantische Suche: Man findet Ergebnisse nach Bedeutung, nicht nur nach Schlüsselwörtern.

FWas ist Cosine Similarity?▾

Misst den Winkel zwischen zwei Vektoren:

  • 1.0 = zeigen in die gleiche Richtung = sehr ähnlich
  • 0.0 = stehen senkrecht = keine Ähnlichkeit
  • -1.0 = zeigen in entgegengesetzte Richtungen

Die Vektordatenbank berechnet Cosine Similarity zwischen der Frage und allen gespeicherten Chunks, und gibt die ähnlichsten zurück.

FWas ist Chunking und welche Strategien gibt es?▾

Große Dokumente müssen in kleine Stücke (Chunks) aufgeteilt werden, weil:

  • Kleine Chunks sind präziser bei der Suche
  • Weniger Tokens = günstiger
  • Context Window hat ein Limit

Strategien:

StrategieWieWann nutzen

Sentence-BasedAn Satzenden schneidenBessere Qualität
Recursive CharacterErst Paragraphen, dann Sätze, dann ZeichenLangChain Standard
SemanticEmbedding-Ähnlichkeit prüfenBeste Qualität, teurer
FNaive RAG vs. Advanced RAG?▾

Naive RAG: Frage → Embedding → Top-K Chunks → LLM. Einfach, aber manchmal ungenau.

Advanced RAG Verbesserungen:

  1. Query Rewriting: LLM formuliert die Frage um für bessere Suche ("Preis?" → "Wie viel kostet eine 3-stöckige Schokoladentorte in Größe L?")
  2. HyDE: LLM generiert eine hypothetische Antwort, die dann als Suchquery dient
  3. Multi-Query: Mehrere Varianten der Frage parallel suchen
  4. Re-Ranking: Top-50 holen, dann mit Cross-Encoder auf Top-5 reduzieren
  5. Hybrid Search: Vektor-Suche + klassische Keyword-Suche kombinieren
In Kidstorte nutzen wir eine Mischung: Bei Preis-Fragen wird die Bestellung als Query umformuliert (Query Rewriting).
FWas ist Hybrid Search?▾

Kombination aus zwei Suchmethoden:

  1. Vektor-Suche (semantisch): Findet ähnliche Bedeutungen ("Kuchen" findet "Torte")
  2. Keyword-Suche (BM25): Findet exakte Wörter ("XL" findet "XL")

Die Ergebnisse werden mit Reciprocal Rank Fusion zusammengeführt. Vorteil: Man bekommt das Beste aus beiden Welten — semantisches Verständnis UND exakte Treffer.

FWas ist Re-Ranking?▾

Problem: Die Vektorsuche gibt Top-K Ergebnisse, aber die Reihenfolge ist nicht immer optimal.

Re-Ranking: Ein zweites Modell (Cross-Encoder) bewertet jedes Ergebnis nochmal genauer:

1. Vektorsuche: Hole Top-50 Chunks (schnell, ungenau) 2. Cross-Encoder: Bewerte alle 50 einzeln (langsam, genau) 3. Ergebnis: Die besten 5 kommen ans LLM

Warum nicht gleich den Cross-Encoder? Er ist zu langsam für 100.000 Dokumente. Deshalb erst grob filtern, dann genau bewerten.

4LangChain
FWas ist LangChain?▾

LangChain ist ein Baukasten für LLM-Anwendungen. Statt alles selbst zu programmieren, bietet es fertige Bausteine:

  • Models: Einheitliche Schnittstelle für OpenAI, Anthropic, lokale Modelle
  • Prompts: Templates, Beispiele, Output-Parser
  • Chains: Mehrere Schritte verketten
  • Memory: Chatverlauf speichern
  • Tools: LLM kann APIs, Datenbanken, Rechner aufrufen
  • Retrievers: RAG-Integration
FWas ist eine Chain?▾

Eine Chain verbindet mehrere Schritte zu einer Pipeline — wie ein Fließband:

# Einfache Chain: Prompt → LLM → JSON-Parser chain = prompt_template | llm | json_parser # Beispiel: chain = ( ChatPromptTemplate.from_template("Klassifiziere: {input}") | ChatOpenAI(model="gpt-4o-mini") | JsonOutputParser() ) result = chain.invoke({"input": "Ich will eine Torte"}) # → {"intent": "order"}

Der | Operator verbindet die Schritte. Das ist LCEL (LangChain Expression Language).

FWas ist LangChain Memory?▾

Memory speichert den Chatverlauf, damit das LLM frühere Nachrichten kennt:

In Kidstorte: Eigenes WindowMemory — max 20 Nachrichten, ältere gelöscht.

Output Parser wandeln die LLM-Antwort (Freitext) in strukturierte Daten um:

  • JsonOutputParser: Erwartet JSON, parsed es automatisch
  • PydanticOutputParser: Validiert gegen ein Pydantic-Schema
  • CommaSeparatedListOutputParser: "rot, blau, grün" → ["rot", "blau", "grün"]

In Kidstorte: Eigene parse_llm_json() Funktion mit Selbstkorrektur — wenn das JSON kaputt ist, schicken wir es nochmal ans LLM.

5LangGraph
FWas ist LangGraph? Unterschied zu LangChain?▾

LangChain Chains sind linear: A → B → C → fertig.

LangGraph erlaubt Schleifen, Verzweigungen und Bedingungen:

LangChain: A → B → C → D (gerade Linie) LangGraph: A → B → [C oder D?] → zurück zu A? (Graph mit Schleifen)

Warum wichtig? Ein Bestellbot muss Fragen wiederholen bis alle Felder ausgefüllt sind. Das ist eine Schleife — mit einer linearen Chain unmöglich.

FWas sind die Kernkonzepte von LangGraph?▾
  1. StateGraph: Der Graph selbst — enthält Nodes und Kanten
  2. Nodes: Funktionen die den State verändern
  3. Edges: Verbindungen zwischen Nodes (fest)
  4. Conditional Edges: "Wenn Intent=order → zum Bestell-Node, wenn Intent=price → zum Preis-Node"
  5. State: Ein Dict/Objekt das durch den Graphen fließt
  6. Checkpointer: Speichert den State (wie unser SessionManager)
graph = StateGraph(AgentState) graph.add_node("classify", classify_node) graph.add_node("ask", ask_node) # Conditional Routing: graph.add_conditional_edges("classify", route_fn, { "order": "ask", "done": END }) graph.add_edge("ask", "classify") # Schleife!
FWas ist ein Checkpointer?▾

Ein Checkpointer speichert den Graph-State nach jedem Schritt. Das ermöglicht:

  • Multi-Turn-Chat: State bleibt zwischen Nachrichten erhalten
  • Human-in-the-Loop: Graph pausiert, wartet auf menschliche Eingabe
  • Time-Travel: Zu einem früheren Zustand zurückspringen

LangGraph bietet: MemorySaver (RAM), SqliteSaver, PostgresSaver.

In Kidstorte: ChromaDB als eigener Checkpointer — gleiche Idee, selbst gebaut.

FWas ist ein Subgraph?▾

Ein Subgraph ist ein Graph innerhalb eines Graphen. Wie eine Funktion, die selbst mehrere Schritte hat:

Haupt-Graph: ├─ Classify → Route ├─ Bestell-Subgraph: ← eigener kleiner Graph │ ├─ check_complete │ ├─ ask_next │ └─ summarize ├─ Preis-Subgraph: │ ├─ retrieve_docs │ └─ calculate_price └─ Bild-Subgraph

Vorteil: Bessere Organisation, jeder Subgraph kann unabhängig getestet und wiederverwendet werden.

FWas ist ein Multi-Agent-Graph?▾

Mehrere spezialisierte Agenten arbeiten zusammen:

Orchestrator ("Manager") ├─ Beratungs-Agent → kennt Tortentrends, macht Smalltalk ├─ Preis-Agent → RAG + Kalkulation ├─ Bild-Agent → Prompt-Engineering + Generierung └─ Termin-Agent → Kalender-Integration

Jeder Agent hat eigene Prompts und eigene Tools. Der Orchestrator entscheidet, welcher Agent die Anfrage bearbeitet.

In Kidstorte: Unsere Nodes sind quasi "Micro-Agenten" — das gleiche Konzept, nur ohne separate LLM-Instanzen.

6LangSmith
FWas ist LangSmith? Wofür braucht man es?▾

LangSmith ist wie ein "Röntgengerät" für LLM-Anwendungen. Man kann sehen, was innerhalb der App passiert.

3 Säulen:

  1. Tracing: Jeden LLM-Call aufzeichnen — welcher Prompt wurde geschickt, was kam zurück, wie lange hat es gedauert, was hat es gekostet
  2. Monitoring: Dashboards mit Metriken — Latenz, Fehlerrate, Kosten über die Zeit
  3. Evaluations: Automatisch prüfen ob die Antworten gut sind
FWie funktioniert Tracing?▾

Jeder Schritt in der App wird als "Run" aufgezeichnet:

Graph-Run (Eltern) ├─ guardrail-Run (Kind) │ └─ LLM-Call: {input: "Hallo", output: "safe", 50ms} ├─ classify-Run (Kind) │ └─ LLM-Call: {input: "Schokotorte...", output: {intent:"order"}, 180ms} └─ ask_next-Run (Kind) └─ LLM-Call: {input: "Frage nach Form...", output: "Welche Form?", 120ms}

Das sieht man als Baum-Ansicht auf smith.langchain.com — man kann in jeden einzelnen LLM-Call reinzoomen.

FWas sind LangSmith Evaluations?▾

Man definiert Testfälle (Input + erwartetes Ergebnis) und lässt das System automatisch prüfen:

Testdatensatz: {input: "Ich will eine Schokotorte", expected: intent="order"} {input: "Was kostet das?", expected: intent="price"} {input: "Hallo!", expected: intent="greeting"} Evaluatoren: - Exact Match: Stimmt der Intent? - LLM-as-Judge: "Bewerte die Antwort auf einer Skala 1-5" - Custom: "Enthält die Antwort einen Preis?"

7AI Agents
FWas ist ein AI Agent? Einfach erklärt.▾

Ein normales LLM ist wie ein Berater: Man fragt, es antwortet.

Ein Agent ist wie ein Mitarbeiter: Er kann selbständig Entscheidungen treffen, Tools benutzen und Aufgaben erledigen.

Normales LLM: Frage → Antwort (einmal) Agent: Frage → Nachdenken → Tool benutzen → Ergebnis anschauen → Nochmal nachdenken → Anderes Tool → ... → Fertige Antwort

Der Agent entscheidet selbst, welches Tool er wann benutzt — und wiederholt Schritte bis die Aufgabe erledigt ist.

FWas ist das ReAct-Pattern?▾

ReAct = Reasoning + Acting. Der Agent "denkt laut":

Thought: Ich muss den Preis nachschlagen. Action: search_knowledge_base("Schokoladentorte Preis") Observation: M: 45€, L: 55€, XL: 65€ Thought: Der Kunde hat 10 Gäste, das ist Größe L. Action: respond("55€ für Größe L")

Das Besondere: Das LLM begründet jeden Schritt, bevor es handelt. Das macht Entscheidungen nachvollziehbar.

FWas sind Tools bei Agenten?▾

Tools sind Funktionen, die das LLM aufrufen kann:

tools = [ {name: "check_calendar", desc: "Prüft Verfügbarkeit an einem Datum"}, {name: "calculate_price", desc: "Berechnet den Tortenpreis"}, {name: "search_products", desc: "Sucht in der Wissensdatenbank"}, {name: "generate_image", desc: "Erstellt ein Tortenbild"}, ]

Das LLM liest die Beschreibungen und entscheidet: "Für diese Frage brauche ich calculate_price."

FWas ist Function Calling / Tool Use?▾

Ein Feature moderner LLMs (GPT-4, Claude): Statt Freitext gibt das Modell ein strukturiertes JSON zurück:

// Input: "Ist am 27. März noch frei?" // LLM-Output: { "function_call": { "name": "check_calendar", "arguments": {"date": "2026-03-27"} } } // Der Code führt check_calendar aus → Ergebnis: "2 Plätze frei" // Das Ergebnis geht zurück ans LLM → "Ja, am 27.03. sind noch 2 Plätze frei!"
FSingle Agent vs. Multi-Agent?▾

Single Agent: Ein LLM mit vielen Tools. Einfach, aber wird bei >10 Tools unzuverlässig.

Multi-Agent: Mehrere spezialisierte Agenten. Jeder hat nur 2-3 Tools.

Single: Ein LLM → [15 Tools] ← wird verwirrt Multi: Chef-Agent (Orchestrator) ├─ Agent A → [Tool 1, Tool 2] ← Spezialist ├─ Agent B → [Tool 3, Tool 4] ← Spezialist └─ Agent C → [Tool 5, Tool 6] ← Spezialist
"Multi-Agent ist wie ein Team: Jeder ist Spezialist für sein Gebiet, und der Chef koordiniert."
FWas ist Plan-and-Execute?▾

Eine Agent-Strategie in zwei Phasen:

  1. Plan: Das LLM erstellt zuerst einen vollständigen Plan ("Schritt 1: ..., Schritt 2: ..., Schritt 3: ...")
  2. Execute: Dann wird jeder Schritt einzeln ausgeführt

Vorteil vs. ReAct: Bei ReAct denkt der Agent nach jedem Schritt neu. Bei Plan-and-Execute gibt es einen übergeordneten Plan, was zu konsistenteren Ergebnissen führt.

FWas ist Human-in-the-Loop?▾

Der Agent pausiert und fragt den Menschen bevor er wichtige Aktionen ausführt:

  • "Soll ich die Bestellung wirklich abschicken?"
  • "Meinen Sie Schokolade oder Vanille?"
  • "Soll ich den Termin am 27.03. buchen?"

In Kidstorte: Das Adressformular und die Bestätigungsvorschau ("Jetzt bestellen") sind Human-in-the-Loop — der Kunde muss explizit bestätigen.

FWas ist Prompt Engineering?▾

Die Kunst, dem LLM die richtigen Anweisungen zu geben. Techniken:

  1. Zero-Shot: Nur Anweisung, keine Beispiele. "Klassifiziere diesen Text."
  2. Few-Shot: 2-5 Beispiele mitgeben. "Beispiel: ‚Schokotorte' → order. Jetzt du: ..."
  3. Chain-of-Thought: "Denke Schritt für Schritt." → besseres Reasoning
  4. Role-Playing: "Du bist ein erfahrener Tortenberater..."
  5. Output-Format: "Antworte als JSON: {intent, data}"
"In Kidstorte nutzen wir alle 5 Techniken: System-Prompt mit Rolle, Few-Shot-Beispiele für Intents, JSON-Format, und explizite Regeln für Sonderfälle."
FWas ist Chain-of-Thought (CoT)?▾

Man bittet das LLM, seinen Denkprozess zu zeigen:

OHNE CoT: "Was ist 17 * 24?" → "408" (falsch!) MIT CoT: "Was ist 17 * 24? Denke Schritt für Schritt." → "17 * 20 = 340. 17 * 4 = 68. 340 + 68 = 408." (richtig!)

Durch das "laute Denken" macht das LLM weniger Fehler bei komplexen Aufgaben. Funktioniert besonders gut bei Mathe, Logik und mehrstufigen Problemen.

FWas ist Grounding?▾

Sicherstellen, dass LLM-Antworten auf echten Fakten basieren, nicht auf Halluzinationen:

  • RAG: Fakten aus Datenbank liefern
  • Zitate: LLM muss Quellen angeben ("Laut Preisliste...")
  • Faktencheck: Zweites LLM prüft die Antwort
  • Structured Output: Nur erlaubte Werte zulassen
FWas ist Multimodalität?▾

Ein Modell, das verschiedene Datentypen versteht — nicht nur Text:

  • Text → Text: Chat, Zusammenfassung
  • Text → Bild: DALL-E, Midjourney (unsere Tortenvorschau!)
  • Bild → Text: GPT-4 Vision ("Was ist auf diesem Bild?")
  • Audio → Text: Whisper (Sprache zu Text)
  • Text → Audio: TTS (Text zu Sprache)

GPT-4o ist nativ multimodal — es versteht Text, Bilder und Audio in einem Modell.

FWie funktioniert Bildgenerierung (Diffusion)?▾

Moderne Bildgenerierung nutzt Diffusion Models (DALL-E, Stable Diffusion, Midjourney):

  1. Forward Process: Ein echtes Bild wird Schritt für Schritt mit Rauschen zerstört (wird zu "TV-Schnee")
  2. Training: Das Modell lernt, diesen Prozess rückgängig zu machen — aus Rauschen ein scharfes Bild zu erzeugen
  3. Generierung: Start mit reinem Rauschen → Schritt für Schritt wird ein Bild daraus, gesteuert durch den Text-Prompt
"Stellen Sie sich vor, Sie zerknuellen ein Foto immer mehr. Das Modell hat gelernt, ein zerknuelltes Foto wieder zu glaetten — und kann so auch komplett neue Bilder aus Rauschen erschaffen."
FWas ist ein Guardrail?▾

Sicherheitsmechanismen, die das LLM vor Missbrauch schützen:

  • Input Guardrail: Prüft die Eingabe BEVOR sie ans LLM geht (Jailbreak? Spam? Toxisch?)
  • Output Guardrail: Prüft die Antwort BEVOR der Nutzer sie sieht (keine Passwörter? keine falschen Versprechen?)

In Kidstorte: Unser guardrail()-Node ist ein Input Guardrail — der allererste Schritt im Graphen.

FWas ist Streaming und warum ist es wichtig?▾

Ohne Streaming: Der Nutzer wartet 3-5 Sekunden, dann erscheint die komplette Antwort auf einmal.

Mit Streaming: Wörter erscheinen Wort für Wort, wie bei ChatGPT. Der Nutzer sieht sofort die ersten Wörter.

Technisch: Server-Sent Events (SSE) — der Server schickt Token für Token an den Browser.

In Kidstorte: /api/chat/stream liefert Wort-für-Wort mit Cursor-Animation.

9Testing & Evaluations
FWie testet man LLM-Anwendungen?▾

Drei Ebenen:

  1. Unit Tests: Einzelne Nodes isoliert testen ("Wenn Input X, kommt Output Y?")
  2. Integration Tests: Ganzen Bestellflow durchspielen ("10 Nachrichten → Bestellung komplett?")
  3. LLM Evaluations: Datensätze mit 100+ Testfällen automatisch prüfen

Das Besondere bei LLMs: Die Ausgabe ist nicht deterministisch! Gleiche Frage → leicht andere Antwort. Deshalb prüft man nicht auf exakte Gleichheit, sondern auf Semantik ("Ist der Sinn richtig?").

FWas ist LLM-as-a-Judge?▾

Man nutzt ein stärkeres LLM, um die Outputs eines anderen LLMs zu bewerten:

Frage: "Was kostet eine Schokoladentorte?" Antwort: "Eine Schokoladentorte kostet 45€ in Größe M." Judge-Prompt: "Bewerte diese Antwort: - Korrektheit (1-5) - Vollständigkeit (1-5) - Höflichkeit (1-5)" Judge-Ergebnis: 4/5

Vorteil: Skaliert viel besser als menschliche Bewertung (100 Testfälle in Sekunden).
Nachteil: Der Judge kann auch falsch liegen.

10Architektur & Sicherheit
FRAG-System für 1 Million Dokumente — wie?▾
  1. Semantic Chunking: Intelligent teilen statt starr alle 500 Zeichen
  2. Pinecone oder Qdrant: Skalierbare Vektordatenbank statt ChromaDB
  3. Hybrid Search: Vektor + Keyword kombinieren
  4. Re-Ranking: Cross-Encoder für Top-50 → Top-5
  5. Metadata Filtering: Vor Vektorsuche nach Kategorie filtern
  6. Caching: Häufige Fragen cachen
FLLM-Kosten um 80% senken — wie?▾
  1. Kleineres Modell: GPT-4 → GPT-4o-mini (33x günstiger)
  2. Caching: Gleiche Fragen nicht doppelt berechnen
  3. Calls reduzieren: 2 Calls zu 1 kombinieren (wie unser classify+extract)
  4. Prompts kürzen: Überflüssige Anweisungen entfernen
  5. Kontext beschränken: Nicht den ganzen Chat mitschicken
  6. Open-Source: Llama 3, Mistral für einfache Tasks

FWas ist Mixture of Experts (MoE)?▾

Ein Architektur-Trick bei modernen LLMs (GPT-4, Mixtral):

Statt alle Parameter für jedes Token zu nutzen, gibt es mehrere "Experten" (Sub-Netzwerke). Ein Router entscheidet für jedes Token, welche 2-3 Experten aktiviert werden.

Token: "Schokolade" Router: Aktiviere Experte 3 (Essen) + Experte 7 (Deutsch) → Nur 2 von 8 Experten rechnen → schneller & effizienter

Vorteil: Das Modell kann riesig sein (viele Parameter), aber bei jedem Token wird nur ein Bruchteil genutzt → schnell trotz Größe.

FWas ist Quantization?▾

Die Parameter eines LLMs werden normalerweise als 32-bit Zahlen gespeichert. Quantization reduziert das auf 16-bit, 8-bit oder sogar 4-bit.

Effekt:

  • 32-bit → 4-bit = Modell ist 8x kleiner
  • Läuft auf günstigeren GPUs oder sogar auf Laptops
  • Leichter Qualitätsverlust, oft kaum merkbar

Beispiel: Llama 3 70B braucht 140GB RAM in 16-bit. In 4-bit nur ~35GB — passt auf eine GPU.
