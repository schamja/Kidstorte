6. LangGraph — Der Agent-Graph

Kidstorte nutzt das LangGraph-Konzept: Ein gerichteter Graph aus Nodes (Verarbeitungsknoten), die durch einen zentralen Router verbunden sind. Jeder Node hat eine klar definierte Aufgabe.

Graph-Architektur (graph.py)

# CakeDreamsGraph — Der zentrale Agent-Graph
# Jeder Durchlauf: User-Input → Guardrail → Classify → Route → Node → Response

class CakeDreamsGraph:
  def run(self, state, user_input):
    state = guardrail(state)         # Node 0: Sicherheit
    state = classify_and_extract(state) # Node 1: Intent + Extraktion
    if intent == "order":
      state = check_complete(state)   # Node 4: Felder prüfen
      if complete:
        state = summarize_order(state) # Node 6: Zusammenfassung
        state = generate_image(state)  # Node 10: Vorschaubild
      else:
        state = ask_next(state)       # Node 5: Nächste Frage
    elif intent == "price":
      state = retrieve_docs(state)   # Node 7: RAG-Suche
      state = calculate_price(state) # Node 8: Preisberechnung
    elif intent == "finalize":
      state = finalize_order(state)  # Node 12: Adressformular
    return state

12 Nodes im Detail

NodeFunktionDateiBeschreibung
0guardrail()nodes.pyBlockiert Beleidigungen, Jailbreaks, Spam
1classify_and_extract()nodes.pyErkennt Intent + extrahiert Bestelldaten in einem LLM-Call
2greet()nodes.pyBegrüßung + erste Frage (Anlass)
3extract_info()nodes.pyStandalone-Extraktion (wird von classify_and_extract ersetzt)
4check_complete()nodes.pyPrüft welche der 10 Pflichtfelder noch fehlen
5ask_next()nodes.pyStellt die nächste fehlende Frage (LLM-generiert)
6summarize_order()nodes.pyZeigt Zusammenfassung aller Bestelldetails
7retrieve_docs()nodes.pyRAG: Sucht in ChromaDB nach relevanten Dokumenten
8calculate_price()nodes.pyBerechnet Preis mit RAG-Kontext
9answer_question()nodes.pyBeantwortet Info-Fragen mit RAG-Kontext
10generate_image()nodes.pyMultimodal: Referenzbild + OpenAI Image API
11update_order()nodes.pyÄndert bereits gegebene Bestelldetails
12finalize_order()nodes.pyZeigt Adressformular, speichert Bild ins Portfolio

Warum LangGraph?

Vorteile

  • Klare Trennung: Jeder Node = eine Aufgabe
  • Flexibles Routing: Intent bestimmt den Pfad
  • Einfach erweiterbar: Neuer Node = neue Funktion
  • Testbar: Jeder Node einzeln testbar

State-Management

  • Ein zentrales AgentState-Objekt
  • Wird durch jeden Node weitergereicht
  • Enthält: order_info, messages, todo, images
  • Persistiert in ChromaDB (Session)

Conditional Routing

  • order_complete? → summarize + image
  • missing_fields? → ask_next
  • has_image? → finalize
  • person_name? → sanitize prompt

7. RAG — Retrieval-Augmented Generation

RAG ermöglicht dem Agent, auf aktuelle, firmenspezifische Informationen zuzugreifen, die nicht im LLM-Training enthalten sind.

RAG-Architektur

1
Dokumente importieren (einmalig)
ingest.py liest Preisliste, FAQ, Allergene, Lieferbedingungen und chunked sie
ingest.py docs/
↓
2
Embeddings erstellen
OpenAI text-embedding-3-small wandelt Chunks in Vektoren um
nodes.py → _llm_embedding() OpenAI Embedding API
↓
3
In ChromaDB speichern
Vektoren + Originaltexte werden in der Vektor-Datenbank gespeichert
ChromaDB Collection "cake_docs"
↓
4
Bei Kundenfrage: Semantic Search
Frage → Embedding → ChromaDB findet die 5 relevantesten Chunks
nodes.py → retrieve_docs()
↓
5
LLM antwortet mit Kontext
GPT-4o-mini bekommt Frage + relevante Dokument-Chunks → präzise Antwort
nodes.py → calculate_price() / answer_question() 1 LLM-Call

Wo wird RAG eingesetzt?

AnwendungNodeDokumenteBeispiel
Preisberechnungcalculate_price()Preisliste mit Größen, Zuschlägen"Was kostet eine 3-Schicht Schoko-Torte für 30 Gäste?"
Info-Fragenanswer_question()FAQ, Allergene, Lieferbedingungen"Habt ihr glutenfreie Optionen?"
Allergie-Infoanswer_question()Zutatenlisten, Allergene-Tabelle"Ist die Vanille-Torte laktosefrei?"

Code-Beispiel: retrieve_docs()

def retrieve_docs(state):
  # 1. Query aus Bestelldaten bauen
  query = "Preis Kuchen Vanille, 30 Gäste, 2 Schichten"

  # 2. Embedding erstellen
  query_embedding = _llm_embedding(query)

  # 3. ChromaDB: Top-5 relevante Chunks finden
  results = collection.query(
    query_embeddings=[query_embedding],
    n_results=5
  )

  # 4. Kontext in State speichern für LLM
  state["rag_context"] = results["documents"]
  return state

8. Memory — Gesprächs-Gedächtnis

Der Agent hat ein mehrstufiges Gedächtnis, das den Gesprächsverlauf und Bestellfortschritt über die gesamte Session hinweg speichert.

3 Ebenen des Memory

1. Short-Term Memory
Messages-Array

  • Letzte 20 Nachrichten (user + assistant)
  • Wird bei jedem LLM-Call als Kontext mitgegeben
  • Ermöglicht: "Ja" → Agent weiß, worauf sich "Ja" bezieht
  • Datei: state["messages"]

2. Working Memory
Order Info + TODO

  • order_info: Alle extrahierten Bestelldaten
  • question_todo: Status jedes Feldes (pending/asked/answered)
  • Überlebt die gesamte Session
  • Datei: state["order_info"], state["question_todo"]

3. Long-Term Memory
ChromaDB Session

  • Gesamter State wird in ChromaDB persistiert
  • Überlebt Server-Neustarts
  • Session-ID via Cookie
  • Datei: session_manager.py

Memory-Fluss

# Jeder Request:
1. session_mgr.load_session(session_id)   ← ChromaDB → State laden
2. state["messages"].append(user_input)    ← Nachricht merken
3. classify_and_extract(state)           ← order_info aktualisieren
4. check_complete(state)                 ← question_todo sync
5. state["messages"].append(response)     ← Antwort merken
6. session_mgr.save_session(session_id, state) ← In ChromaDB speichern

question_todo — Fortschritts-Tracking

# Jedes Pflichtfeld hat einen Status:
question_todo = {
  "anlass":     "answered",  # ✅ Beantwortet
  "gaeste":     "answered",  # ✅ Beantwortet
  "geschmack":  "answered",  # ✅ Beantwortet
  "dekoration": "asked",    # ⏳ Gefragt, noch offen
  "allergien":  "pending",   # ○ Noch nicht gefragt
  ...
}

Matching-Score Algorithmus

KriteriumScoreBeispiel
Figur/Motiv im Dateinamen+2 pro Wort"elsa" in "elsa_3_etagen.png" → +2
Etagen-Match+1"3_etagen" in Dateiname und Bestellung → +1
Farb-Match+1"blau" in Dateiname und Bestellung → +1
Anlass-Match (Hochzeit)+2"hochzeit" in Dateiname → +2
Minimum-Score≥ 2Unter 2 = kein Match → normale Generierung

Dual-Modus: cal.com + Lokaler Fallback

🌐 cal.com API (wenn konfiguriert)

  • GET /v2/slots — Freie Zeitfenster abfragen
  • POST /v2/bookings — Termin buchen bei Finalize
  • Echtzeit-Synchronisation mit externem Kalender
  • Unterstützt Event-Types und Team-Kalender

🗄️ Lokaler Fallback (SQLite)

  • count_orders_on_date() aus order_db.py
  • Max. Bestellungen/Tag aus prompts_config.yaml
  • Öffnungszeiten + Ruhetage konfigurierbar
  • Kein externer Service nötig

Validierungsregeln

  • ⏰ Mindestens 2 Tage Vorlauf (Zubereitung braucht Zeit)
  • 🚫 Ruhetage werden automatisch abgelehnt (Standard: Sonntag)
  • 📊 Kapazitätsgrenze pro Tag (konfigurierbar in Admin)
  • 🔄 Bei Ablehnung: 5 Alternative Termine werden vorgeschlagen
