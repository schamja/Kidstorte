Projektuebersicht

Kidstorte ist ein intelligenter, KI-gestuetzter Bestellassistent fuer eine Konditorei. Das System fuehrt Kunden im Chat durch den gesamten Bestellprozess – von der Geschmackswahl bis zur Bildvorschau der Wunschtorte. Es kombiniert vier fortschrittliche KI-Technologien:

TechnologieEinsatz im Projekt
RAG (Retrieval-Augmented Generation)Produktwissen, Preisregeln, Herstellungsprozesse
LangGraph-Style State MachineGespraechssteuerung mit Intent-Routing und Knotenlogik
Session Memory (ChromaDB)Gespraechsverlauf und Bestellstatus ueber mehrere Nachrichten
Multimodale Modelle (GPT-4o Vision)Referenzbilder erkennen, vergleichen und als Vorlage nutzen

Alle Dateien und ihre Verbindungen

main.py – Der Empfang (verbindet sich mit ALLEN anderen Dateien)

main.py ├── importiert graph.py → startet KI-Durchlauf ├── importiert session_manager → laedt/speichert Gespraeche ├── importiert order_db.py → speichert Bestellungen ├── importiert config.py → liest Einstellungen ├── importiert monitoring.py → zaehlt Metriken ├── importiert cost_optimizer → schaetzt Token-Kosten ├── importiert email_service → schickt E-Mails └── importiert pdf_order.py → erstellt PDFs

main.py ist der FastAPI-Server und Einstiegspunkt der Anwendung. Er nimmt HTTP-Anfragen entgegen, verwaltet Session-Cookies und verbindet alle Module miteinander.

graph.py – Der Dirigent

graph.py ├── importiert nodes.py → ruft jeden KI-Schritt auf ├── importiert state.py → kennt das Klemmbrett-Format └── LOGIK: entscheidet welcher Node wann aufgerufen wird

graph.py enthaelt die CakeDreamsGraph-Klasse und entscheidet, welcher KI-Schritt als naechstes kommt. Er ist der Regisseur – stateless, speichert selbst keine Daten.

nodes.py – Das Herzstueck

nodes.py ├── importiert config.py → liest Prompts aus YAML ├── importiert state.py → liest/schreibt AgentState ├── importiert error_handler.py → Fehler abfangen ├── nutzt OpenAI API → GPT-4o-mini (Text + Vision) ├── nutzt OpenAI API → gpt-image-1 (Bilder generieren) ├── nutzt HuggingFace API → FLUX/SDXL (Backup-Bilder) └── nutzt ChromaDB → RAG Wissensbasis durchsuchen

nodes.py fuehrt alle KI-Aufgaben aus: Intent erkennen, Daten extrahieren, Preise berechnen, Bilder generieren. Jede Funktion ist mit @safe_node dekoriert, um Fehler abzufangen.

state.py – Das Klemmbrett

state.py (das Klemmbrett) ← graph.py liest und schreibt ← nodes.py liest und schreibt ← session_manager.py speichert und laedt ← main.py liest die finale Antwort

state.py definiert den AgentState – ein TypedDict mit allen Informationen, die zwischen den Verarbeitungsschritten geteilt werden. Es ist die „Single Source of Truth“.

config.py – Die Konfigurationszentrale

config.py ← liest .env Datei (API-Keys, Passwoerter) ← liest prompts_config.yaml (KI-Anweisungen) → gibt alles an nodes.py, main.py, email_service, etc.

config.py liest alle Umgebungsvariablen und die Prompt-Konfiguration. Hot-Reload: Bei Aenderungen an der YAML-Datei wird sie automatisch neu geladen – ohne Server-Neustart.

Kurzuebersicht: main.py startet alles · graph.py steuert den Ablauf · nodes.py fuehrt KI-Schritte aus · state.py speichert den Zustand · config.py liefert Einstellungen

ChromaDB vs. SQLite – Der Unterschied

ChromaDB = Kurzzeitgedaechtnis
  • Speichert aktive Gespraeche (Sessions)
  • Speichert RAG-Wissensbasis (Embeddings)
  • Sessions laufen nach 24h ab
  • Wird bei jeder Chat-Nachricht aktualisiert
SQLite = Langzeitgedaechtnis
  • Speichert abgeschlossene Bestellungen
  • Speichert Kundenbewertungen
  • Bleibt fuer immer erhalten
  • Wird nur bei Bestellabschluss geschrieben

RAG – Retrieval-Augmented Generation

RAG bedeutet „Suche + KI-Antwort“: Die KI antwortet nicht aus dem Kopf, sondern schlaegt zuerst in einer Wissensdatenbank nach. So liefert sie praezise, faktenbasierte Antworten statt Halluzinationen.

Ohne RAG 
Kunde: "Was kostet ein Schoko-Kuchen?"
KI: erfindet einen Preis → halluziniert
Mit RAG 
Kunde: "Was kostet ein Schoko-Kuchen?"
System: sucht in ChromaDB
→ findet: "Schokolade ab 35EUR"
KI: antwortet mit echtem Preis

Schritt 1 – Wissen einlesen (ingest.py)

ingest.py ist der „Bibliothekar“ – er liest alle Dokumente, zerstueckelt sie und sortiert sie ein:

documents/
  ├── preise.md
  ├── faq.md
  └── allergene.md
        │
        ▼
ingest.py liest jede .md Datei
        │
        ▼
chunk_by_sections() → zerstueckelt bei "## Ueberschriften"
        │
        ▼
OpenAI Embedding → jeder Chunk wird zu Zahlen umgewandelt
  "Schokolade kostet 35EUR" → [0.23, -0.84, 0.41, ...]
        │
        ▼
ChromaDB speichert: Text + Zahlen + Quelle

Schritt 2 – Wissen abrufen (nodes.py → retrieve_docs)

Kundenfrage: "Was kostet das?"
       │
       ▼
Frage auch zu Zahlen umwandeln
  → [0.22, -0.85, 0.40, ...]
       │
       ▼
ChromaDB vergleicht mit allen gespeicherten Zahlen
  → findet aehnlichsten Chunk (= Preisliste)
       │
       ▼
KI beantwortet mit echtem Inhalt

Was ist ein Embedding?

Ein Embedding wandelt Text in Zahlen um, die seine Bedeutung beschreiben. Aehnliche Bedeutung = aehnliche Zahlen:

"Was kostet Schoko?"     → [0.229, -0.851, 0.408, ...]
"Schokoladenkuchen 35EUR"  → [0.231, -0.847, 0.412, ...]
                                │
                         fast identisch! ChromaDB findet den richtigen Chunk

Bewertung der RAG-Staerke

Staerken
  • Antwortet NUR mit Infos aus echten Dokumenten
  • Keine erfundenen Preise oder Infos
  • Automatisch aktuell nach neuem Ingest
  • Doppeltes Einlesen wird verhindert (Chunk-ID-Check)
Schwaechen
  • Nur bei intent = "price" oder "info" aktiv
  • Bestelldetails kommen NICHT aus RAG
  • Nur .md Dateien unterstuetzt
Bewertung: Mittelstark – gut fuer Preise und FAQ, nicht fuer die eigentliche Bestelllogik

LangGraph-Style State Machine

LangGraph ist NICHT installiert. Das Projekt nutzt ein selbst gebautes LangGraph-Muster – gleiche Idee, eigener Code. Das zeigt ein tiefes Verstaendnis der Konzepte.

LangGraph ist eine Idee: „Ein Agent ist ein Graph aus Knoten (Nodes)“. Jeder Node ist eine Funktion, die etwas macht. Kanten (Edges) verbinden die Knoten.

# Echter LangGraph wuerde so aussehen:
from langgraph.graph import StateGraph  # ← gibt es hier NICHT

# Kidstorte macht es selbst in graph.py:
class CakeDreamsGraph:
    def run(self, state, user_input):
        state = guardrail(state)           # Schutzplanke
        state = classify_and_extract(state) # Intent + Daten
        if intent == "order":
            state = extract_info(state)    # Details extrahieren
            state = check_complete(state)   # Alles da?
        return state

Wie der Workflow funktioniert

  • guardrail(state) – Prueft ob die Eingabe zulaessig ist (keine Beleidigungen, kein Jailbreak)
  • classify_and_extract(state) – Ermittelt die Absicht (Intent) des Nutzers und filtert erste Informationen aus dem Text
  • Logik-Weiche – Je nach Intent wird in den passenden Modus geschaltet (Bestellung, Preis, Bild, Info, etc.)
  • extract_info(state) – Sucht nach Details (z.B. „Schokotorte“, „12 Personen“)
  • check_complete(state) – Prueft ob alle noetige Informationen vorhanden sind

Vergleich: Echtes LangGraph vs. Kidstorte

FunktionEchtes LangGraphKidstorte
Nodes (Schritte)JaJa (nodes.py)
Routing (Weichen)JaJa (graph.py)
State (Klemmbrett)JaJa (state.py)
Checkpointer (Speicher)JaJa (session_manager.py)
StreamingJaJa (/api/chat/stream)
Bibliothek installiertJaNein (selbst gebaut)
Fazit: Kidstorte ist ein LangGraph-Klon – gleiche Idee, eigener Code.

Multimodales RAG – Text und Bilder verstehen

Monomodal

Versteht NUR Text.
KI liest: „Ich will Elsa-Dekoration“ → antwortet

Multimodal

Versteht Text UND Bilder gleichzeitig.
KI sieht Referenzfoto + liest Kundenwunsch → erstellt passendes Bild

Die Vision-Pipeline (3 Schritte in nodes.py)

SCHRITT 1: _scan_reference_images + _find_best_reference
  ↓ Laedt alle Bilder aus "Bilder/" Ordner (mit Cache)
  ↓ Schickt sie an GPT-4o-mini Vision (detail: "low" fuer Kostenersparnis)
  ↓ GPT sieht jedes Bild, vergleicht mit Kundenwunsch
  ↓ Gibt zurueck: "Bild 2 passt am besten (Score: 0.85)"

SCHRITT 2: Detaillierte Beschreibung
  ↓ GPT-4o-mini beschreibt das beste Bild auf Englisch:
  "Fondant figurine of ice queen with platinum blonde braid,
   snowflake decorations, blue and white color scheme..."
  ↓ Diese Beschreibung wird zur VORLAGE fuer die Bildgenerierung

SCHRITT 3: generate_single_image
  ↓ gpt-image-1 bekommt: Vorlage + Kundenwuensche
  ↓ Prompt: BASE DESIGN (Referenz) + CUSTOMER CHANGES (Farbe, Etagen)
  ↓ Generiert neues Bild das Vorlage aehnelt aber Wuensche umsetzt

Automatisches Portfolio-Wachstum

_auto_save_to_reference() erkennt automatisch prominente Figuren (Elsa, Ronaldo, Batman, Spiderman, etc.) in der Dekoration und speichert generierte Bilder im Bilder/-Ordner. Das Portfolio waechst mit jeder Figurentorten-Bestellung.

Das Prompt-System – Wie gut ist es?

Wo stecken alle Prompts?

prompts_config.yaml ├── classify_intent → Was will der Kunde? (greeting/order/price/...) ├── extract_info → Welche Details hat er genannt? ├── ask_next → Was soll ich als naechstes fragen? ├── calculate_price → Berechne Preis als HTML-Tabelle ├── answer_question → Beantworte allgemeine Fragen ├── image_description → Beschreibe Kuchen in einem Satz ├── greet → Begruessungstext └── redirect → Zurueck zum Thema fuehren

Die drei Prompt-Kategorien

1. Strategische Prompts (Steuerung)
  • classify_intent – Der „Tuersteher“: Ordnet Kundennachrichten in Kategorien ein
  • redirect – Die „Leitplanke“: Lenkt hoeflich zurueck zu den Torten
2. Daten-Sammler (Extraktion & Logik)
  • extract_info – Der „Detektiv“: Scannt „Vegane Torte fuer 10 Personen am Samstag“ und extrahiert strukturierte Daten
  • calculate_price – Der „Buchhalter“: Gibt Preise als HTML-Tabelle aus
3. Antwort-Module (Interaktion)
  • greet + ask_next – Begruessung und naechste Frage (mit TODO-System)
  • answer_question – Beantwortet Fragen mit RAG-Kontext
  • image_description – Kurze Bildbeschreibung in einem Satz

Was macht das Prompt-System besonders stark?

1. Hot-Reload – Prompts aendern sich ohne Server-Neustart 
# config.py prueft bei jedem Aufruf ob YAML geaendert wurde
mtime = os.path.getmtime(PROMPTS_CONFIG_PATH)
if mtime != _prompts_cache["mtime"]:
    # Neu laden!
2. Kombinierter Classify+Extract Call – spart 50% Kosten 
# nodes.py – Ein einziger API-Call fuer zwei Aufgaben:
combined_prompt = classify_prompt + extract_prompt
# → gibt zurueck: {"intent": "order", "extracted": {"geschmack": "Schoko"}}
3. TODO-Listen-System – fragt nicht dieselbe Frage zweimal 
question_todo = {
  "anlass":    "answered",  # schon beantwortet
  "gaeste":    "asked",     # gefragt, noch keine Antwort
  "geschmack": "pending",   # noch nicht gefragt
}
4. Halluzinations-Schutz

STRENGSTE REGEL: Extrahiere NUR was der Kunde WOERTLICH gesagt hat!
ERFINDE NIEMALS Werte!
Namen BUCHSTABENGENAU uebernehmen! (Aron bleibt Aron, nicht Aaron!)

1. Seite oeffnen
main.py gibt Session-Cookie aus → session_id = "abc123"
2. Erste Nachricht
„Hallo, ich moechte einen Kuchen fuer meinen Sohn“
→ guardrail OK → classify: intent=„order“ → extract: {anlass: Geburtstag}

→ gpt-image-1: BASE DESIGN + CUSTOMER CHANGES
→ _auto_save: Torte wird in Bilder/ gespeichert
6. Bestellung finalisieren
„Perfekt, bestellen!“ → intent = „finalize“ → show_address_form = True

POST /api/submit-order → order_db.save_order() → PDF erstellen → E-Mail an Kunde + Designer
8. Admin setzt Status „fertig“

Alle Module im Detail

session_manager.py – Das Gedaechtnis

Der SessionManager speichert den kompletten AgentState fuer jede aktive Sitzung in ChromaDB. So „erinnert“ sich der Agent an fruehere Nachrichten, auch wenn der Browser-Tab geschlossen wird.

Ablauf pro Chat-Nachricht:
  1. Browser sendet Cookie (session_id)
  2. session_mgr.load_session(id)  → State aus ChromaDB laden
  3. graph.run(state, user_input)   → State verarbeiten
  4. session_mgr.save_session(id, state) → zurueckspeichern

Sessions laufen nach SESSION_TTL_HOURS (24h) ab. cleanup_old_sessions() wird beim Server-Start automatisch aufgerufen.

order_db.py – Das Kassenbuch

Speichert abgeschlossene Bestellungen dauerhaft in einer SQLite-Datenbank (kidstorte.db).

orders Tabelle:
  id, session_id, order_info (JSON), customer_name, customer_email,
  customer_phone, customer_street, customer_plz, customer_city,
  liefertermin, total_price, status, created_at

ratings Tabelle:

Wichtige Design-Entscheidungen

Stateless Graph
Agent speichert keine Daten. State lebt extern in ChromaDB – leicht testbar und skalierbar.
Kombinierter LLM-Call
classify_and_extract() spart ~50% API-Kosten pro Nachricht.
Zwei Datenbanken
ChromaDB fuer Sessions (24h), SQLite fuer Bestellungen (dauerhaft).
Graceful Degradation
E-Mail/PDF-Fehler stoppen nicht die Bestellung – nur Logging.
